The HN Take

Memory that computes

The traditional computer architecture is that processors compute and memory remembers. This creates a bottleneck, because the processor has to keep asking memory for data over an external bus that is much slower than the bandwidth available inside the memory chip. Samsung's solution is straightforward: Put little processors in the memory.

Its LPDDR5X-PIM chip places a processing block next to each of 16 memory banks. Together those blocks can access 614 gigabytes per second of internal bandwidth, versus 76.8 gigabytes per second through ordinary DRAM accesses. The memory can do multiply-accumulate operations on model weights without first shipping all the weights to a CPU or GPU. Great.

Also Samsung wants the chip to work with a standard memory controller. There are no standard commands for telling DRAM to do arithmetic, because traditionally DRAM has not done arithmetic. So Samsung uses special row addresses to change what ordinary memory commands mean. In normal mode, a read command reads memory. In PIM mode, a read command initiates computation. A write command might write memory, or it might load a PIM register, or it might tell the PIM block to write its results somewhere. Context is important.

This preserves hardware compatibility but creates some software complications. For instance, while one thread is using PIM, another thread cannot safely access the same memory channel, because its innocent read might accidentally initiate a computation. Multiple processes cannot independently use PIM. Interrupts and context switches are difficult because the operating system would have to exit PIM mode and save the state spread across the memory banks.

Also caches are a problem, because they might absorb commands that were supposed to trigger computation, while PIM can modify data without telling the caches. So Samsung recommends mapping PIM memory as uncacheable. Speculative execution and prefetching are also problems, because modern processors routinely issue reads whose results they might not need, and here those reads have side effects. "Running a CPU without caching, prefetching, or out-of-order execution will cripple performance," notes the article.

Still, the memory works with a standard modern computer. You just have to turn off the parts that make the computer modern.

Pointer maturity

Here is a nice long-term software bug. Since Go 1.14 in 2020, its runtime has stored two kinds of values in an eight-byte Linux event field: a raw pointer for an internal event object, and a tagged pointer for sockets. This worked fine on 64-bit systems. On 32-bit little-endian systems, though, the runtime compared only the lower four bytes.

Unfortunately the lower four bytes of a tagged socket pointer contain a counter called fdseq. If a Go program runs long enough and recycles enough socket objects, that counter eventually reaches the same value as the address of the internal event object. The runtime then mistakes a socket for its own event file descriptor, receives an event it does not expect and crashes.

The counter generally has to reach millions, which is why the bug appeared only in long-running programs and went unnoticed for years. The researchers built a reproducer that predicted a crash around cycle 2,240,520 and triggered it within a few minutes. They fixed the problem by representing the internal event descriptor as a tagged nil pointer, so both kinds of entries use the same format.

Their speculative conclusion is that Google "no longer runs any 32-bit Go programs," because otherwise it would presumably have encountered the bug. This is one way for a software platform to end 32-bit support: not officially, but by waiting three million sockets and seeing who calls.

1. Samsung's Processing-in-Memory (PIM)

chipsandcheese.com | ingve | 108 points | 30 comments | discussion

First seen: August 29, 2026 | Consecutive daily streak: 1 day

Analysis

Samsung’s LPDDR5X-PIM technology integrates compute-capable processing units directly into DRAM banks, allowing for high-bandwidth, in-memory operations like multiply-accumulate (MAC) without relying on the traditional bottleneck of the external memory bus. By repurposing standard DRAM commands to toggle between memory and processing modes, Samsung enables this functionality to run on existing memory controllers, theoretically expanding its compatibility across a wide range of devices. However, this implementation introduces significant software and architecture hurdles, as the required disabling of CPU caching, prefetching, and out-of-order execution severely hampers system performance. Ultimately, the technology highlights the potential for energy-efficient AI acceleration, but it also demonstrates that widespread adoption will likely require fundamental changes to how memory subsystems handle coherence and multitasking.

4. Hunting Down a Go Runtime Bug on 32-Bit Embedded Systems

sigma-star.at | birdculture | 25 points | 2 comments | discussion

First seen: August 29, 2026 | Consecutive daily streak: 1 day

Analysis

Researchers identified a persistent, long-standing bug in the Go runtime that caused sporadic fatal crashes in long-running applications on 32-bit little-endian ARM and i386 Linux systems. The issue stemmed from an accidental memory alias where the runtime's internal `netpoll` mechanism confused socket file descriptors with event file descriptors because their underlying 8-byte data structures overlapped on 32-bit architectures. By creating a reproduction case, the team demonstrated that the crash occurred only after the internal `fdseq` counter reached values matching the memory address of `netpollEventFd` after millions of cycles. The maintainers merged a fix that replaces the ambiguous raw pointer with a tagged `nil` pointer, effectively resolving the aliasing issue. This finding highlights the risks of neglecting 32-bit platform support in modern language runtimes, as the bug had persisted undetected for several years before being addressed.

Comment Analysis

The reaction was brief and largely sympathetic to the report’s implications rather than disputing its technical findings. One commenter offered a practical debugging resource, while another focused on the broader concern that similar 32-bit defects may remain undiscovered.

Better debugging tools — A minority, single-comment perspective emphasizing that stronger debugger tooling—particularly GDB’s Python interface—can materially improve embedded-systems investigation. This was adjacent to the specific Go bug rather than a direct assessment of it.

Analysis

TurboKV is a new, high-performance embedded key-value store written in Rust that focuses on asynchronous operations and configurable durability modes. It supports atomic batching, ordered range scans, and background compaction, utilizing hardware-accelerated AES for its persisted Bloom filters. Designed for developers requiring flexible trade-offs between speed and data persistence, the library provides distinct durability presets ranging from fast in-memory execution to strict, sync-heavy consistency. By offering competitive benchmarks against existing Rust storage engines, TurboKV aims to provide an efficient solution for applications needing granular control over I/O behavior and storage performance.

Analysis

The release of htmx 4.0 marks a significant architectural shift for the library, primarily by moving its underlying network implementation from `XMLHttpRequest` to the modern `fetch()` API.
