Ears.

Here is a general optimization strategy: Stop solving a harder problem than you have.

A GPU fills triangles. A digital map is mostly polygons, so before the GPU can draw buildings, parks and "the strip of grass between two tram tracks," the map engine has to cut every polygon into triangles. GLOBUS's offline map of the region around Warsaw has 3,740,425 polygons at one zoom level, and its constrained Delaunay triangulator took 2.93 seconds on one M4 Pro core to cut them up.

Delaunay triangulation produces nicely shaped triangles. This is useful if you are interpolating values across them or running a simulation. But:

A flat fill doesn't care: a GPU fills a needle-thin triangle as correctly as a fat one.

Right. The old system was carefully optimizing the aesthetic quality of invisible triangles underneath parking lots.

So GLOBUS replaced it with ear clipping. An "ear" is a convex corner of a polygon that can be sliced off as a triangle without crossing the rest of the boundary. Cut off an ear, repeat, and eventually the entire park has been reduced to triangles. A theorem guarantees that there is always another ear to cut, which is reassuring in both computational geometry and corporate restructuring.

The simplest ear clipper took 1.12 seconds, already 2.6 times faster than the Delaunay code. Then came the usual sequence of indignities inflicted on beautiful mathematics in production software: test only the dents, skip tests on convex polygons, write triangle strips, sort things into buckets. The resulting library, earstrip, processes the 3.7 million polygons in 489 milliseconds and is faster than earcut in both C++ and the browser.

Almost half of the polygons have four vertices or fewer. A triangle requires no cutting, and a convex quadrilateral requires one diagonal. The Delaunay implementation nevertheless spent 419 milliseconds constructing proper triangulations for them from scratch. Sometimes your sophisticated algorithm is losing because it approaches every garden shed as a research problem.

Fake terminal.

Oh good:

There's no shell or filesystem behind it: every keypress goes in, and the model predicts how the screen changes.

WorldTUI is a 360 million parameter language model trained to pretend to be a terminal. It can apparently create files, run vim and tmux, play snake and "usually remembers what you wrote a few commands later." It is not executing commands. It is predicting what a terminal screen would probably look like after you typed them.

The author suggests typing "pythoon" to expose the illusion. A real terminal will boringly tell you that the command does not exist; the model has seen enough Python sessions that it may decide to be helpful and run Python anyway. This is the inverse of normal software reliability. Correct spelling gets you a plausible computer, while a typo lets you glimpse the void.

There is a sensible research idea here. A terminal is a compact world model: It is a grid of characters, training data can be generated by recording real shells, and a coding model already knows what commands like "ls" and "cat" tend to print. The model was fine-tuned on 336,000 recorded episodes, about 2 billion tokens, and then compressed and quantized to a 208 megabyte browser download.

But the central question is whether it maintains a consistent world or merely generates convincing output. The answer is: somewhat. In a memory test, WorldTUI correctly recovered 9 of 13 file values, versus 2 or 3 for prompted base models. On the other hand:

It's still far from a reliable filesystem. It handles familiar commands fairly well, but combining them in new ways can quickly break things. For example, after echo green >> colors, running cat colors often doesn't show the appended line.

Traditionally the useful property of a filesystem is that files continue to contain what you wrote into them. WorldTUI has reproduced the appearance of computing while treating persistence as an aspirational feature.

This is perhaps the purest version of learned software. Instead of writing a shell, filesystem, editor and game, you train a model on what those programs look like and ask it to improvise all of them. The terminal is no longer an interface to a computer. It is a role played by a language model, and sometimes it forgets its lines.

3.7 Million Polygons, Triangulated in 489 Milliseconds

globus.software  ·  42 pts  ·  2 comments

GLOBUS’s earstrip turns sprawling map geometry into GPU-ready triangles with an optimized C++ and WebAssembly pipeline. The library keeps difficult polygons in view while shaving time from a familiar rendering bottleneck.

Read →Share →
[ Analysis + ]

Technical Analysis

GLOBUS has released earstrip, an ISC-licensed C++ and WebAssembly polygon triangulator designed for map rendering, where millions of buildings, parks, and other polygons must be converted into GPU-friendly triangles. It replaces a constrained Delaunay approach with optimized ear clipping, using reflex-vertex tracking, spatial buckets, branch-reduced containment checks, triangle strips, and fallbacks for difficult or hole-heavy geometries. On 3.74 million map polygons, it runs in 489 ms natively versus 557 ms for earcut.hpp, and is 1.4–2.1 times faster than earcut.js in browser-oriented tests. The work matters because triangulation is a significant cost in offline and web map rendering, while the library preserves correctness on problematic rounded map data and can return compact strips suitable for WebGL and WebGPU.

A Small Model Pretends to Be a Terminal

simedw.com  ·  241 pts  ·  78 comments

WorldTUI trains a 360-million-parameter model to predict terminal screens from keystrokes, without running a real shell or filesystem. It is compact, local, and entertaining—and still loses the plot when unfamiliar commands arrive.

Read →Share →
[ Analysis + ]

Technical Analysis

WorldTUI is an experiment that fine-tunes a 360M-parameter Qwen coding model to simulate a terminal by predicting screen updates from individual keypresses, without running a real shell or filesystem. Trained on 336,000 synthetic sessions from Dockerized shells and applications, it can imitate bash, vim, tmux, Python, and Snake while retaining limited state, though it remains unreliable in unfamiliar command combinations and file operations. The project’s main technical advances are compact screen-delta encoding, self-correction training, parallel row decoding, and int4 quantization, enabling a 208 MB model to run locally in a browser via WebGPU. Its importance is as a practical demonstration that small language models can learn aspects of an interactive application’s behavior and maintain a weak internal world state, while also revealing how quickly consistency and memory degrade without explicit underlying rules.

Technical Analysis

David Harvey assesses a bold AI-generated claim that integer multiplication can be performed in \(O(n(\log n)^{1-\varepsilon})\) bit operations, improving on the long-standing \(O(n\log n)\) bound. The story is important both for the potential breakthrough in a foundational computational problem and for its unsettling demonstration that an AI system may be producing mathematical research beyond what its human users can readily understand or check.

google.github.io  ·  318 pts  ·  191 comments  ·  discussion

Analysis

Google’s Rust Style Guide establishes conventions for formatting, code organization, API design, ownership, error handling, traits, concurrency, documentation, unsafe code, and testing across Google codebases such as Android, Chromium, Fuchsia, and ChromeOS. It generally follows ecosystem standards while adding rules intended to improve readability, maintainability, automation, and large-scale refactoring. The guide distinguishes library code, which should prioritize flexible and reusable APIs, from application code, where simplicity and directness matter more. Its recommendations include using small crates, avoiding glob imports and unnecessary shared ownership, preferring standard traits and derived implementations, choosing `Option`, `Result`, or panics appropriately, and favoring clear, refactor-friendly interfaces.
