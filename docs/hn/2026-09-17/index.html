Maintainer infrastructure

Servo says that one year of donations funded longtime maintainer Josh Bowman-Matthews to work part-time on improving the browser engine's contributor experience. Here is the accounting:

"I nominated 8 new maintainers

"I reviewed 1150 pull requests

"I filed 114 issues targeted at newer contributors (92% of them have been fixed)"

He also wrote documentation, diagnosed unexpected failures and fixed intermittent tests.

This is a nice illustration of what open-source software funding actually buys. Intuitively, you donate to a browser engine because you want more browser engine. Someone writes a rendering feature, the browser renders more things, progress. But a large collaborative software project is not constrained exclusively by the supply of code. It is also constrained by the supply of people who review the code, explain why the tests failed, turn large intimidating problems into small approachable issues and notice that the test failure is caused by broken window.open behavior rather than by the contributor's patch.

There is a sort of leverage here. Bowman-Matthews did not personally fix all 114 newcomer issues. He filed them, and other people fixed 92% of them. He supported a rewrite of Servo's JavaScript engine integration partly by reviewing pull requests and partly by breaking the work into issues that could be distributed across contributors. The donations paid for one part-time maintainer, but the maintainer organized unpaid and separately funded work by many other people. Open-source middle management.

This sounds less glamorous than writing a browser engine, but possibly it is more useful. If you have 100 volunteer programmers and nobody reviews their pull requests, you do not have 100 programmers. You have a large inbox. The essential infrastructure for a lightweight, high-performance browser engine turns out to include a person whose job is to tell newcomers what to do and reassure them that the flaky test is not their fault.

Recursive self-improvement

Z.ai has a report titled "Toward Recursive Self-Improvement: How GLM Built Its Own Inference Infrastructure," which gets right to the point:

"Today, GLM-5.3 has become an indispensable daily coding partner for everyone on the team, and it is moving steadily toward replacing us."

Sure. Z.ai says an Infra Agent powered by GLM-5.3 did much of the work of building a production inference system for GLM-5.3-Flash on more than 100,000 Chinese-made AI accelerators. The system went from initial adaptation to production readiness in less than two weeks, and optimization tripled end-to-end throughput. The resulting model then processed more than 62 trillion tokens in six days after launching anonymously on OpenCode and OpenRouter.

There is a straightforward self-referential loop here. The model writes code that makes the model cheaper and faster to run. A cheaper, faster model can write more code. Eventually the model designs and trains its successor autonomously, or so the maximalist version goes. Z.ai calls this recursive self-improvement and writes that "our successors are the AI systems we are creating ourselves," which is an arresting way to announce an infrastructure optimization project.

But the detailed account is a little less mystical and perhaps more useful. The agent did not gaze upon the inference stack, understand it completely and produce the answer. Engineers defined objectives and system boundaries. They built an experimental environment with correctness tests, logs, execution traces, runtime events, microbenchmarks and end-to-end metrics. The agent proposed hypotheses, changed code and used those tools to determine whether its changes worked.

Z.ai calls this "dense feedback." The important thing was not giving the model more logs. It was making feedback local, cheap, timely and objectively verifiable. "Throughput dropped by 20%" tells the agent that it made things worse. A kernel comparison or execution trace can tell it where and perhaps why. If every experiment answers one narrow question, the agent can iterate without waiting for an experienced engineer to connect six different profiling tools by intuition.

This is arguably a general lesson about AI coding agents. Giving an agent access to your codebase is useful. Giving it fast tests that identify exactly how it failed is much more useful. The model can only improve itself after the humans have carefully arranged the world so that every mistake produces a legible error message.

That is still a significant capability. A model helped build the infrastructure that serves the model, at large scale, on an immature hardware ecosystem, and apparently did work that Z.ai says would previously have taken experienced engineers weeks. But the early form of recursive self-improvement looks less like an intelligence explosion and more like extremely ambitious continuous integration. First the AI replaces the infrastructure team. Before that, the infrastructure team has to write it very good tests.

Uncovering the Hidden Keys Behind U.S. Driver License Barcodes

ryan.science  ·  186 pts  ·  67 comments

A security audit reveals that most states deploy digital signatures on driver licenses without publishing the necessary public verification keys. This failure leaves the technology as a closed-off black box, preventing independent verification of identity documents.

Read →Share →
[ Analysis + ]

Technical Analysis

Security researcher Ryan Fahey explains that while many U.S. driver's licenses contain cryptographically signed PDF417 barcodes, these signatures are often functionally useless because the issuing states fail to publish the necessary public keys or documentation. By analyzing the data structures used by vendors like Canadian Bank Note and IDEMIA, Fahey successfully reverse-engineered the signing process and recovered public keys for several states, enabling independent verification of license authenticity. While California has adopted a transparent, documented system that allows public verification, most other states continue to deploy similar technology as an undocumented "black box." This creates a significant security gap where the engineering for robust identity verification exists but remains dormant, leaving states reliant on visual, physical anti-counterfeiting measures instead of modern, verifiable digital standards.
