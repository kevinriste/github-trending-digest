Blender without Blender.

Here is a sensible software thesis: If millions of people have spent decades using a user interface, perhaps the valuable part is not just what it looks like but all the tiny things it has learned to do.

BUI extracts Blender's interface into a standalone library with a small C core. It handles layout, input and drawing in native code, and can be driven from Python, Rust, JavaScript, C, C++, React, Svelte and Dear ImGui. It does not require Blender, and the JavaScript version does not ship a browser.

The pitch is partly performance. Blender's interface "redraws only what changed, sleeps when nothing does, and starts in milliseconds." But the more interesting product is accumulated muscle memory:

"You press a number field and drag: the cursor vanishes, the value glides under your hand, and you never hit the edge of the screen. You type 2*pi into a field and it just works. You type 'ad cu' into a menu and it finds 'Add Cube'."

Right. A new UI framework can draw a button. The harder task is knowing that artists want to type equations into number fields, drag across several checkboxes, search for Add Cube by entering two partial syllables, and manipulate a value without eventually running out of mousepad. Those are not grand architectural insights. They are decades of small complaints fossilized into code.

BUI's approach is to take those fossils and put adapters on them. Existing tkinter programs can supposedly run unchanged while looking less like 1998. Rust developers can use HTML, CSS and Tailwind without a browser. React and Svelte can produce native windows. Dear ImGui can become Blender. Qt syntax is partially supported. There is even a roadmap entry for MyGo, whose current status is "Not yet (coming soon)," which is also a reasonable description of many UI frameworks.

Software developers periodically conclude that every existing interface toolkit is wrong and should be replaced with a cleaner one. BUI proposes the opposite: The old interface has already survived millions of users doing strange things to it, so perhaps the efficient move is to remove the 3D modeling application and keep the sliders.

257-character password.

A locked Unix account can have an asterisk in its password field. The asterisk is not a password hash, so no password should ever match it. This is an old, simple and reassuring convention.

Except, reportedly, in one particular combination of OpenSSH, musl libc, no PAM and password authentication. There, an account that should accept no password can accept any password between 257 and 1024 characters.

The path to this result is made entirely of reasonable decisions. Some password-hashing functions return NULL when they cannot process a password or salt, and programs that fail to check can crash. Musl therefore returns a one-character failure value instead. SHA-512 password hashing also becomes slower as the password gets longer, which creates a denial-of-service opportunity, so musl refuses passwords longer than 256 bytes.

Separately, OpenSSH once had a user-enumeration problem. A nonexistent or password-disabled user could be rejected immediately, while a real user took longer because the server hashed the attempted password. Attackers could time the difference. The fix was to hash a password anyway, using another account's salt, before returning no.

Put those decisions together with the asterisk sentinel and, on the affected configuration, the failure value can match the locked account field. The system does all the extra work required to conceal whether an account exists and then lets you into it.

The report says the affected setup requires musl, OpenSSH without PAM, password logins enabled, an account whose password field is just an asterisk, and another account with a real password. It names Alpine, OpenWrt, Buildroot and Yocto as relevant musl environments. On Alpine's official AWS and Azure images, it says, the default alpine user is affected and has passwordless doas, so the result is root. Glibc systems, PAM configurations, Dropbear and OpenBSD are described as unaffected.

This is a pleasingly complete example of security composition. The locked-account marker is safe. The crash-prevention behavior is safe. The password-length cap is safe. The timing-attack mitigation is safe. Stack all four safety mechanisms together and a sufficiently long wrong password becomes correct.

The researcher found it by building OpenSSH across different libc, PAM and shadow configurations and throwing about 17,600 unusual login attempts at them, with help from "agent swarms." Every build agreed except musl without PAM. People inspect the cryptography; the password bypass was waiting in the boring code where OpenSSH talks to libc.

On affected systems, password security therefore has an unusual shape. More length is better until character 256. Character 257 removes the password requirement.

Blender’s Interface Escapes the Blender Shell

github.com  ·  274 pts  ·  107 comments

BUI extracts Blender’s widget system into a standalone native runtime for Python, Rust, JavaScript, C, and C++. The project trades browser overhead for damage-based redraws, compact binaries, and a familiar power-user vocabulary—still with bindings and platforms under construction.

Read →Share →
[ Analysis + ]

Technical Analysis

BUI is an open-source project that extracts Blender’s widget rendering and interaction model into a standalone, C-based UI runtime accessible from Python, Rust, JavaScript/React, C/C++, and Dear ImGui. It aims to provide Blender-like controls and themes—including specialized editors, sliders, menus, and expression-aware fields—without requiring Blender, a browser, or a webview. The project emphasizes low resource use through native rendering, damage-based redraws, optional GPU acceleration, and small standalone binaries, claiming benchmark advantages over gpui in CPU usage, memory, and startup time. Its significance is that it could let developers reuse Blender’s mature, efficient interaction design across desktop tools and artist-oriented applications, though several bindings and platform features remain incomplete or experimental.

A Long Password Can Open a Locked SSH Account

sshhole.com  ·  2748 pts  ·  664 comments

OpenSSH on musl-based systems mishandled passwords longer than 256 characters, potentially bypassing accounts whose password field was meant to disable login. Update to OpenSSH 10.6p2, disable password authentication, and inspect Alpine, OpenWrt, Buildroot, and Yocto deployments.

Read →Share →
[ Analysis + ]

Technical Analysis

The story describes a long-standing OpenSSH authentication flaw on musl-based Linux systems such as Alpine, OpenWrt, Buildroot, and Yocto when PAM is disabled or unused. Because musl’s `crypt()` rejects passwords over 256 bytes in a way OpenSSH mishandles, accounts whose password field is `*`—intended to forbid password login—may accept any password between 257 and 1024 characters if another account has a valid password hash. This can affect key-only users, root, LDAP accounts, and default users in some Alpine cloud images, potentially enabling unauthorized root access when password authentication remains enabled. The issue was missed because common glibc, PAM, and OpenBSD configurations are unaffected, and it has been addressed in OpenSSH 10.6p2; administrators should update or disable password authentication and review affected deployments.

Analysis

The story describes a long-standing OpenSSH authentication flaw on musl-based Linux systems such as Alpine, OpenWrt, Buildroot, and Yocto when PAM is disabled or unused. Because musl’s `crypt()` rejects passwords over 256 bytes in a way OpenSSH mishandles, accounts whose password field is `*`—intended to forbid password login—may accept any password between 257 and 1024 characters if another account has a valid password hash. This can affect key-only users, root, LDAP accounts, and default users in some Alpine cloud images, potentially enabling unauthorized root access when password authentication remains enabled. The issue was missed because common glibc, PAM, and OpenBSD configurations are unaffected, and it has been addressed in OpenSSH 10.6p2; administrators should update or disable password authentication and review affected deployments.
