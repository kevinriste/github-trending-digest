LineageOS 24.0

LineageOS has released version 24.0, based on Android 17, and for once the custom Android project is early:

"We were able to rebase onto Android 17's code-base faster than anticipated. Yes you read that right: We're early this year!"

This is partly because Google has spent several Android releases heavily refactoring everything, forcing LineageOS to adapt, and those adaptations have now made adapting easier. Sufficiently sustained platform instability eventually becomes institutional expertise.

The release adds updated core apps, streamed system updates and browser-based tools for flashing devices over ADB, Fastboot, Amlogic Burn and Samsung Odin. Traditionally, installing a custom operating system involved finding the correct desktop utility, installing drivers, reading several pages of device-specific instructions and trying not to turn your phone into a decorative rectangle. Now a website can help you turn your phone into a decorative rectangle directly.

LineageOS is careful about this:

"As always, flashing custom software carries risk. Back up anything important, confirm that you have selected the correct files and device, and follow the instructions presented by the tool."

Right. The browser can communicate directly with your phone's low-level installation machinery, but please read carefully before clicking. Web applications have progressed from displaying documents to rewriting boot partitions.

The larger point of LineageOS is keeping old devices useful long after their manufacturers lose interest. Security patches through October 2026 have been merged into versions going back to LineageOS 18.1, and even older branches have patches through November 2025. Some devices with Linux kernels 4.4 and 4.9 will remain capped at LineageOS 22.2 because carrying their "rather hacky" platform changes into newer Android releases has become too difficult.

Your old phone can live forever, but eventually it becomes less of a phone and more of a community-maintained historical reenactment of one.

Decision model

Here is a useful way to make a language model faster: Don't let it talk.

A normal model asked for structured JSON still generates the response token by token. But if the possible answers are fixed, say A through E, you can mask the rest of the vocabulary and inspect the probabilities of those five tokens after a single pass. The model becomes a multiple-choice machine whose entire expressive range is five letters.

This works reasonably well. A 1.7 billion parameter Qwen model scored 59.38% on a sample of CommonsenseQA, improving to 62.41% after fine-tuning. But there is an important distinction between "the model is 99.78% likely to emit A" and "A is 99.78% likely to be correct." Asked where one would most likely find a bat, it assigned 99.78% to "Cave," despite "Baseball game," "Attic," "Zoo" and "Sporting goods store" all being plausible depending on which bat everyone had in mind.

The model was not 99.78% sure where bats are. It was 99.78% sure that, having seen this question, it wanted to say A. This is less an epistemological judgment than a strong autocomplete preference.

Across the evaluation, predictions in the 90% to 100% confidence range were correct only about 70% of the time. Temperature scaling improved the calibration by flattening the probabilities, without changing the underlying answers. In other words, the model's decision-making became more trustworthy after leaving its decisions alone and making it sound less certain about them.

This is also a useful model of executive judgment. Pick one of five options immediately, then hire someone to calibrate the confidence afterward.

Analysis

IRCv3 is an initiative to modernize and standardize extensions to the long-established IRC chat protocol while preserving compatibility with older clients and servers. Its specifications cover features such as SASL authentication, account information, message metadata, away notifications, server timestamps, and message grouping. The working group is also developing standards for account registration, chat-history access, secure-connection upgrades, Unicode names, and client avatars. The project matters because it provides a common, interoperable path for IRC networks and software developers to add contemporary chat capabilities without abandoning IRC’s established ecosystem.

4. Build your own decision model

nishtahir.com | softwaredoug | 323 points | 74 comments | discussion

First seen: October 11, 2026 | Consecutive daily streak: 1 day

Analysis

The article explains how to turn a language model into a fast “decision model” for tasks with a fixed set of answers by examining one next-token distribution and masking all other outputs, rather than generating a full response. Using a 1.7B Qwen model on CommonsenseQA, the author achieves about 59% accuracy without fine-tuning and 62% after fine-tuning, showing that small models can support practical classification workflows. However, raw token probabilities are highly overconfident and should not be interpreted as reliable correctness estimates. Applying temperature scaling substantially improves calibration, which is important when model predictions inform downstream automation, prioritization, or risk-sensitive decisions.

Reactions ranged from praise for the guide and interest in practical uses to debate over whether decision models are meaningfully distinct from existing methods. 8. How big is a Git commit?

ratfactor.com | theanonymousone | 39 points | 19 comments | discussion

First seen: October 11, 2026 | Consecutive daily streak: 1 day

Analysis

The article examines how much disk space Git commits consume, emphasizing that the answer depends on file compressibility, repository tree size, and whether Git has packed and deduplicated its objects. Experiments show substantial fixed overhead for tiny changes—about 8–17 KB for a few bytes in small repositories—because a commit can create commit, tree, and blob objects. Larger files are stored more efficiently: a 584 KB binary used about 298 KB, while a 16.4 MB source file used about 1.6 MB in loose-object storage. The findings are important for understanding Git’s storage behavior, especially why small commits can seem disproportionately expensive while larger, repetitive content benefits from compression and packing.

The comments mostly add technical context rather than dispute the article’s findings. They distinguish the apparent cost of loose objects from the longer-term cost after packing and delta compression, while also discussing compression choices, Git’s fit with distributed storage, shell-script readability, and measurement details.
