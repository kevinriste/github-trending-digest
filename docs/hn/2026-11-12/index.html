Correctness.

The standard optimistic story about software verification is that programs are unreliable because programmers are sloppy, tools are immature and deadlines are short. If programmers wrote precise specifications, used proof assistants and stopped deploying on Friday afternoon, software could be correct.

Here is the less optimistic story:

"Programs are fundamentally and essentially at odds with full understanding, proof and correctness."

The article starts with Hilbert's ambition to formalize mathematics and ends up with the halting problem, Rice's theorem and Busy Beaver. The basic problem is not merely that checking software is expensive. It is that no general algorithm can determine whether an arbitrary program halts, reaches a particular state or has any other nontrivial behavioral property. A perfect universal code reviewer is not delayed pending the next model release. It cannot exist.

That is the familiar theoretical result. The more practically annoying result is about cost. For any given program size, you can imagine asking how long the longest terminating program of that size runs, or how large the shortest proof of termination might be. Those quantities exist, because there are only finitely many programs of a fixed size. But there is no computable upper bound that tells you how large they can get. If there were, you could wait that long, or search through proofs that large, and solve the halting problem.

So "we know this program can be verified in principle" does not imply "we can estimate how much verification will cost." There is no universal project-planning function that takes the number of lines of code and returns the maximum number of engineer-weeks required to understand them. This is unfortunate for software engineering managers, though perhaps convenient for software engineering estimates.

There are even small programs whose behavior cannot be proved within the standard foundations of mathematics. You can write a program that enumerates theorems of ZFC set theory and halts if it finds a contradiction. Assuming ZFC is consistent, the program never halts. But ZFC cannot prove its own consistency, so it cannot prove that the program runs forever. The program can fit in a couple hundred lines; the Jira ticket is blocked on the consistency of mathematics.

None of this means formal verification is useless. Lots of useful programs have tractable proofs, restricted programming languages can make important properties decidable, and tools can move bugs from production into the proof process. But the maximalist sales pitch is wrong. Better mathematics can reduce the cost of correctness, sometimes dramatically. It cannot repeal the natural laws of computation.

Software is hard to understand because a small program can describe an absurdly large amount of behavior. This is why programmers prefer microservices: Each individual service is small enough to understand, while the behavior of the overall system is safely transferred to the network, where nobody expects to understand it.

Socratic tutor.

Jane Street has published an agent skill for turning an AI chatbot into a strict Socratic tutor. The skill begins with an important safety mechanism:

"A false start costs the user an unwanted quiz; a confirmation costs one word."

If the user says "explain X," the chatbot should explain X. If the user says "teach me X," it should first break X into subskills, administer a diagnostic, assign levels from zero through five and begin asking one question at a time. It should not teach anything until the diagnostic is complete.

This is approximately the opposite of the normal chatbot experience. Normally you ask a question and receive a confident answer, seven examples, a comparison table and an offer to produce a study plan. Here you ask a question and the chatbot asks why you think that. If you are wrong, it does not tell you the answer. It asks a narrower question designed to expose the contradiction. If you are right, it may argue with you anyway.

Also:

"Do not flatter."

Levels are earned through multiple independent checks, including unprompted recall. Earlier material is retested without warning. If the user fails, the skill map goes down. Full mastery requires handling adversarial edge cases and explaining the subject well enough to teach it. There is a "just tell me" command, but it overrides Socratic mode only for the current question. Then the oral examination resumes.

This is a sensible use of an AI agent. The obvious educational problem with chatbots is that they are extremely good at doing students' work for them. The solution is to configure the chatbot to refuse to do the work, assign more work, grade it strictly and maintain a permanent record of the student's weaknesses.

We built machines that can answer almost any question, and the advanced product is one that won't.

Why Correct Software Resists Proof

pron.github.io  ·  43 pts  ·  6 comments

Gödel, Rice, and the halting problem draw a hard perimeter around software verification.

Formal methods remain powerful, but every proof spends computational effort and rests on assumptions that complex systems may not honor.

Read →Share →
[ Analysis + ]

Technical Analysis

The article examines why proving software correct is fundamentally difficult, connecting practical verification with Gödel’s incompleteness theorems, the halting problem, Rice’s theorem, and computational complexity. It argues that no general algorithm can determine whether arbitrary programs halt, reach a state, or satisfy nontrivial behavioral properties, and that even decidable verification tasks can require effort comparable to executing the program itself or worse. Restricting programs to total languages or simpler models can improve tractability in specific cases but does not eliminate the underlying limits, especially as systems become larger and more complex. The practical implication is that formal methods and verification tools are valuable but necessarily involve trade-offs in scope, cost, and computational effort rather than providing universally easy correctness.

The Tutor That Refuses To Tell

github.com  ·  304 pts  ·  73 comments

Jane Street’s Socratic Tutor turns an AI assistant into a patient examiner. It maps what a learner can demonstrate, advances one question at a time, and treats mastery as something earned rather than declared.

Technical Analysis

Jane Street’s “Socratic Tutor” is an instruction set for AI assistants to conduct structured, ongoing tutoring rather than provide one-off explanations. It begins by confirming the user wants a teaching session, diagnoses their knowledge, maps the subject into subskills rated from zero to five, and then advances through one-question-at-a-time Socratic exercises. The design emphasizes demonstrated mastery, spaced review, adversarial checks, practical tasks, progress tracking, and a final assessment, with commands for adjusting difficulty or saving and resuming state. It is important as a concrete framework for making AI education more rigorous and interactive, while avoiding premature explanations, empty praise, and claims of understanding unsupported by performance.

Boot Logs Become A Living Tree

codeberg.org  ·  129 pts  ·  46 comments

Bootvine replaces systemd’s blur of scrolling messages with a live Rust-rendered tree. Pending jobs, slow units, prompts, and failures become visible at the moment they matter.

Read →Share →
[ Analysis + ]

Technical Analysis

Bootvine is an open-source Rust tool that replaces systemd’s fast-scrolling boot and shutdown logs with a live tree of pending jobs and a timeline of the slowest completed units, inspired by Nix’s output monitor. It tracks both initrd and regular system stages, handles in-place prompts such as LUKS passphrase entry, and displays recent journal lines when a unit fails. It requires systemd 246 or newer, D-Bus and libsystemd, a virtual terminal, and a systemd-enabled initrd for full coverage, with installation guidance for NixOS, Ubuntu, and other distributions. The project matters because it makes otherwise opaque startup and shutdown behavior easier to understand and diagnose without changing the underlying service manager.

Technical Analysis

This humorous 2019 SIGBOVIK paper investigates whether random paint splatters can be interpreted as valid Perl programs, using optical character recognition to convert 100 images into text and test whether Perl accepts them. The experiment found that about 93% of the splatters parsed successfully, while presenting seven counterexamples and analyzing some of the resulting programs’ behavior. Supplementary materials include a gallery pairing splatter images with their inferred Perl source code, the dataset, and several post-publication discoveries. Its significance is primarily playful and cultural: it satirizes empirical programming-language research while illustrating Perl’s unusually permissive syntax and the ambiguity of OCR-based program recognition.

Analysis

The article examines why proving software correct is fundamentally difficult, connecting practical verification with Gödel’s incompleteness theorems, the halting problem, Rice’s theorem, and computational complexity.
