Phone computer

Here is a hardware procurement strategy:

A developer needs "a high resolution camera, GPS, storage, and a microcontroller to control some lights." The natural approach is to buy a Raspberry Pi 4, an Arducam camera, GPS, storage and eventually various add-on boards for a clock, battery, touchscreen and mobile data. The core setup costs about $222; the more complete one costs roughly $347 plus batteries.

Or:

"Phones like these turn up second hand on Taobao for roughly ¥300-500 (£33-56 / €40-67 / $45-75)."

The phones already have 40- or 50-megapixel cameras, GPS, storage, clocks, batteries, touchscreens and 5G. They also have USB-C ports for connecting the custom light controller. Apparently the cheapest way to assemble a small computer is to buy an extremely mass-produced small computer whose previous owner no longer wants it.

This is not entirely surprising. A Raspberry Pi is cheap relative to a normal general-purpose computer, but it is a component. A phone is an entire finished consumer product assembled at vast scale, depreciated for a few years and then sold into a used market that mostly values it as an unfashionable phone rather than as a camera-equipped GPS computer with cellular networking. The old phone comes with a free touchscreen because nobody wants that touchscreen anymore.

There are drawbacks. The Redmi had to be unlocked and rooted. The Huawei is harder to root. A "50MP JPEG file does not, by itself," prove that its camera beats the Arducam. And while finding two used phones is easy, finding hundreds with matching hardware, healthy batteries and predictable camera behavior is a supply-chain problem.

Still, the basic economics are compelling. If you need one programmable device with a camera, battery, screen, GPS and modem, you can buy all those parts separately. Or you can buy a phone and spend your engineering budget persuading it that it is not a phone.

Ggml 1.0

Ggml has reached version 1.0.0, which means, among other things, that it has pruned deprecated APIs, bumped its RPC protocol to reject incompatible peers and added performance work across CUDA, Metal, Vulkan, SYCL, OpenCL, WebGPU, Hexagon, CPU, CANN, ZDNN and OpenVINO.

This is what local AI infrastructure looks like. The high-level product pitch is "run a model on your device." The underlying engineering pitch is "support every conceivable definition of device."

There are new few-row quantized matrix multiplications on CUDA, fused mixture-of-experts routing on Metal, FlashAttention prefill on Vulkan, a device-side MoE scheduler on SYCL, decomposed Adreno FlashAttention in OpenCL, more operations on Hexagon and assorted CPU kernels. Also the scheduler now avoids uploading inputs that are not read, an optimization with the pleasing general principle that computers are faster when they do not move data they will never use.

The release is called 1.0, but the interesting milestone is less that ggml is finished than that local inference has become a sufficiently real computing layer to require this much hardware diplomacy. You write one model runtime, and then negotiate separately with every chip ever placed in a laptop, graphics card, browser or phone. The model is universal. The matrix multiplication is extremely local.

ggml Reaches a Cleaner 1.0

github.com  ·  293 pts  ·  46 comments

API cleanup lands alongside faster kernels, broader accelerator support, FP8, YaRN controls, and a new RPC protocol. ggml 1.0 makes local inference infrastructure more portable without pretending the hardware differences disappeared.

Read →Share →
[ Analysis + ]

Technical Analysis

ggml v1.0.0 is a major release of the tensor and machine-learning backend used by projects such as llama.cpp, focused on cleaning up its public API while improving portability and performance. It removes deprecated interfaces and legacy diagnostic operations, adds configurable YaRN truncation, FP8 support, better precision handling, and a newer RPC protocol that rejects incompatible peers. Much of the release targets hardware acceleration, including optimized quantized matrix operations, MoE scheduling and fusion, FlashAttention paths, and expanded kernels across CUDA, Metal, Vulkan, SYCL, OpenCL, WebGPU, Hexagon, CPU, and other backends. The release is important because it establishes a cleaner 1.0 API while broadening efficient local inference support across GPUs, mobile and embedded processors, and specialized accelerators.

Borders Without Spending a Cell

joshka.net  ·  287 pts  ·  125 comments

A proposed terminal protocol treats borders as cell-edge attributes instead of characters occupying screen space. If terminals and TUI frameworks adopt it, panes, charts, and forms could gain richer geometry without corrupting copied text.

Read →Share →
[ Analysis + ]

Technical Analysis

The article proposes a draft terminal protocol for drawing borders on cell edges as attributes rather than using box-drawing characters that consume rows and columns. Implemented experimentally in Ghostty and Ratatui, it supports colored, variably wide, styled, rounded, and prioritized lines that scroll, reflow, and interact with text like other cell properties, while allowing TUIs to fall back to conventional borders when unsupported. This could improve panes, popups, forms, buttons, checkboxes, and charts, preserve usable screen space, and prevent borders from contaminating copied text. Adoption remains uncertain because terminals, multiplexers, and TUI frameworks would need protocol support, and rendering complexity, interoperability, and resource costs still require testing.
