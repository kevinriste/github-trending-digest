The HN Take

Going nowhere

A programming language has two main customers. One is the people designing the language, who want to keep improving it. The other is the people using the language, who would like it to stop improving quite so much.

Here is a critique of Zig:

Zig has been under development for more than a decade. It remains at version 0.x, without a firm date for a stable 1.0 release.

There is nothing inherently wrong with a long development cycle or a version number below 1.0. Plenty of useful software operates under so-called 0ver.

But Zig is a programming language, not a bundler.

Right. If you are building a programming language, you want to discover the best possible syntax, standard library, compiler and build system. If you are building software in that programming language, you want the syntax, standard library, compiler and build system that you used yesterday. These goals are not perfectly aligned.

Zig's solution has largely been to prioritize the first group. Releases keep changing interfaces, and users keep rewriting their code. This is all properly documented, which is useful in the sense that the project tells you exactly why your program no longer works.

There is a reasonable argument that this is what version 0.x means. Zig has not promised stability, so users cannot complain that it is unstable. But after more than a decade, that becomes less of a versioning policy and more of a business model. Zig's maintainers get a perpetual language-design laboratory, while Zig's users provide free regression testing and repeatedly migrate their applications.

There is also an unusually broad ban on AI-assisted contributions. No generated code, editing, translation, brainstorming or bug finding. The maintainers explain their approach with the poker maxim: "You play the person, not the cards." They want long-term contributors who deeply understand the project, not drive-by patches produced with tools they distrust.

This is coherent if Zig is a community for developing compiler engineers. It is less coherent if Zig is infrastructure. Sometimes a person finds a bug, fixes the bug and then goes back to the unrelated thing she was trying to accomplish before the programming language assigned her a character-building exercise.

And then Bun left. Bun had been a prominent production user of Zig, but in July rewrote its Zig codebase in Rust, citing memory-safety concerns and the burden of maintaining compiler modifications. Zig's leadership responded with a lengthy public attack on Bun's engineering, management and culture, later revising the post and acknowledging resentment in the original framing.

A programming language cannot prevent users from leaving. It can, however, make leaving socially unpleasant, which is perhaps a form of retention strategy. If your code keeps breaking, your contributions are judged partly by your approved development habits, and your departure may inspire an official denunciation, you will certainly think carefully before adopting the language. Very carefully.

Secure enclave

Here is a successful security project:

I have decided to NOT go with the native macOS Secure Enclave approach (using only out-of-the-box tools) because it ended up plain ugly and I can't live with that. However, it is a fully functional, working solution that I would definitely use otherwise.

The author wanted SSH private keys that malware could not copy from his filesystem. Recent versions of macOS can create a non-exportable key inside the Secure Enclave, require Touch ID for every signing operation and expose only a reference file to SSH. The private key never appears on disk or in ordinary memory. This is, from a security perspective, pretty good.

Unfortunately the Touch ID dialog says "ctccardtoken needs to authenticate to continue."

There are many possible threat models in computer security. An attacker might steal your laptop, compromise your account, read your files or execute malicious code. Apple built a hardware-backed system that can protect an SSH key even if the Mac is compromised. It did not protect the user from an ugly low-level framework name.

The setup is also not exactly invisible. You create a CryptoTokenKit identity with sc_auth, export a key handle with ssh-keygen, set SSH_SK_PROVIDER to Apple's provider library and explicitly tell SSH about the resulting identity file because it does not automatically discover that filename. Then every connection produces the unlovely biometric prompt. The cryptography is polished; the product is several shell commands wearing a trench coat.

There is one other catch: The key cannot be backed up. If the Mac dies, the key dies with it. That is not a bug but the direct consequence of making the key impossible to extract. Perfect protection against theft is also perfect protection against recovery. The suggested solution is to enroll another key from another Mac or a YubiKey on every server.

So the final architecture is: Keep an unextractable key on your Mac, keep another unextractable key somewhere else in case the first unextractable key becomes permanently inaccessible, and reject the whole native setup because the authentication dialog lacks Apple's usual aesthetic standards. Security succeeded at every level except typography.

2. Protecting SSH Keys with macOS Secure Enclave

Analysis

The article describes how to create hardware-backed SSH keys on macOS using the Secure Enclave, so private keys never appear on disk or in memory and each use can require Touch ID. It explains the setup with `sc_auth`, OpenSSH’s Secure Enclave provider, SSH configuration, and public-key installation, while noting pitfalls such as outdated instructions, key-discovery issues, and conflicts with other SSH agents. The approach improves protection against malware or filesystem theft without requiring third-party software, but its CryptoTokenKit authentication prompt is poorly polished and the keys cannot be exported or backed up. Because losing the Mac also loses the key, users should maintain an additional key on another device or hardware token; the author may instead use Secretive for a better interface.

7. Greg Kurtzer's Ginux is now a userspace kernel

github.com | d3Xt3r | 83 points | 40 comments | discussion

First seen: November 11, 2026 | Consecutive daily streak: 1 day

Analysis

Ginux has pivoted from an experimental standalone Rust kernel into a userspace kernel that runs as an ordinary Linux process and provides isolated workloads with explicit, versioned compatibility contracts. It intercepts managed system calls and can emulate them, mediate narrowly validated host operations, or deny them, while virtualizing processes, identities, devices, filesystems, and kernel views around a pinned Rocky Linux userspace. The project aims to offer a more reviewable boundary than unrestricted Linux for workloads such as AI agents, but differs from seccomp and related systems by treating the entire instance interface and lifecycle as one configurable contract. Its current Rocky/systemd baseline is research software—not complete Linux compatibility or production-grade containment—with performance, coverage, and escape boundaries still under testing.

Comment Analysis

The reaction was curious but cautious. Commenters debated whether a userspace kernel’s narrower interface can reduce exposure, or whether it adds another kernel-like component that must itself be trusted. They compared Ginux with namespaces, User-mode Linux, gVisor, and VMs, weighing security, compatibility, performance, and maturity. Others questioned the project’s durability and the role of AI-assisted development, while some argued that AI assistance alone does not settle its value or trustworthiness.
