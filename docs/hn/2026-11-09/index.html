Mainframe in a container

Here is a modern way to own a 1970s mainframe:

docker run -it --name vm370 -p 3270:3270 rbanffy/vm370ce

This launches VM/370 Community Edition, an extensively improved version of the last VM/370 release that IBM made available without a restrictive license. It runs on an emulated mainframe with one CPU and 16 megabytes of memory, or "storage," because even the terminology requires emulation.

You then connect through a 3270 terminal emulator, log in as CMSUSER with the password "CMSUSER," and begin computing. The guide notes that putting the password after the username "horrifies me even more than having the username as the password," and advises against exposing the machine directly to the internet. The late 1960s had already invented virtual machines and browser-like screen forms, but had not fully developed the concept of people on the internet stealing your mainframe.

There is something pleasingly recursive here. VM/370 creates a virtual machine in which it starts CMS. The whole mainframe is itself emulated inside a Docker container on your ordinary computer. You use a modern virtualization system to run an old virtualization system so that the old virtualization system can create a virtual computer for you. Eventually you reach the actual BASIC program, which prints "HELLO WORLD."

The FORTRAN program is more demanding. It writes "HELLO WORLD FROM FORTRAN" to an oddly named file rather than the terminal, so you redirect file 6 with FILEDEF. Then the first character disappears, apparently because it is being interpreted as a line-printer control character. Nobody is entirely sure. This is authentic vintage computing: The computer works, the output is somewhere, and the missing letter is probably a printer.

Next concepts

The traditional way for a language model to generate text is one token at a time. This is intuitive, but slow: To produce a thousand tokens, the model has to make a thousand sequential decisions. Diffusion language models can work on many positions in parallel, but repeatedly process the whole sequence and lose quality when you reduce the number of sampling steps.

Researchers at Stanford propose a third approach, Next-Concept Modeling. A VQ-VAE first represents text as a hierarchy of discrete codes, from coarse to fine. A transformer generates one level at a time, predicting all the codes within that level in parallel, and the final hierarchy is decoded back into text.

At matched parameter scales, the paper says the method achieved better generative perplexity than its strongest diffusion baseline on the One Billion Word benchmark while running 21 times faster. On OpenWebText it was competitive while running 10 times faster, and on XSum it matched the strongest diffusion model's ROUGE-L score while running 31 times faster. It also beat autoregressive and diffusion baselines on Sudoku while using fewer function evaluations.

The branding is slightly ambitious. The model's "concepts" are learned discrete codes, not necessarily concepts in the sense of "justice," "mortality" or "where did I leave my keys." But the basic idea is appealing: Instead of writing the sentence from left to right, first generate a crude latent plan and then fill in progressively finer detail.

This is also approximately how people are told to write. Start with an outline, refine the structure, add the sentences, fix the words. The important breakthrough is doing all the words in each stage simultaneously, which remains difficult for people unless they are writing a committee report.

A Faster Route Through Text Generation

arxiv.org  ·  109 pts  ·  13 comments

Next-Concept Modeling replaces repeated diffusion sampling with a hierarchy of coarse-to-fine codes predicted in parallel.

On modest models and selected benchmarks, the paper reports substantially fewer function evaluations and faster generation, while leaving scale and generality open to question.

Read →Share →
[ Analysis + ]

Technical Analysis

The paper introduces Next-Concept Modeling (NCM), a non-autoregressive text-generation approach designed to address diffusion language models’ many expensive sampling passes. It first compresses text into a hierarchy of coarse-to-fine discrete residual VQ-VAE codes, then uses a transformer to predict all codes at each level in parallel before decoding the completed representation into tokens. In experiments with roughly 100M-parameter models, NCM reportedly matches or exceeds diffusion baselines while using 4–16× fewer function evaluations, running 10–31× faster on tasks such as LM1B, OpenWebText, XSum, and Sudoku, and requiring 4–5× fewer training tokens; MBR sampling can further improve quality. The main significance is a different quality–latency tradeoff for serving language models, though the results are early, benchmark-specific, and rely on a separately trained tokenizer and relatively small models.

A License Plate Could Open the Door

shubs.io  ·  411 pts  ·  183 comments

A chain of exposed services, hardcoded credentials, authorization failures, and an MFA bypass turned a car’s license plate into a starting point for account takeover. The resulting tokens could unlock vehicles and start engines across multiple countries. Fix the identity stack, not just the dashboard.

Read →Share →
[ Analysis + ]

Technical Analysis

Security researchers found a chain of vulnerabilities in an automaker’s connected-car infrastructure that could let an attacker control vehicles by starting with only a license plate. Publicly exposed admin and identity services, hardcoded credentials in JavaScript, insufficient API authorization, a WAF bypass, and an authentication flow that allowed MFA to be skipped enabled account takeover and the minting of valid mobile-app tokens. Those tokens could then issue commands such as unlocking doors or starting engines through the telematics API; related research extended the impact to vehicles in Australia, the United States, and Canada. The incident highlights how weaknesses across vendor tools, identity management, deployment configuration, and connected-car APIs can combine into a serious real-world safety and privacy risk.

Dragging Becomes a State-Transition Problem

declarative-dragging.github.io  ·  586 pts  ·  76 comments

Declarative Dragging asks authors to describe the states an object may reach, then lets the system synthesize geometry, feedback, and animation. Its demos show how a model-driven approach can make intricate interactions composable rather than hand-coded one gesture at a time.

Read →Share →
[ Analysis + ]

Technical Analysis

“Declarative Dragging” presents D2, a model-driven approach that lets interface authors define which application states an object can reach when dragged, rather than manually coding geometry, feedback, and animation. The system speculatively renders those future states, determines where the dragged element would appear, and synthesizes the interaction, with composable modifiers for behaviors such as snapping, floating, and transitions. Its Dragology web library implements the approach for SVG interfaces, with demonstrations including mathematical and diagrammatic tools whose linked representations update during a drag. The work is important because it could make sophisticated, domain-specific drag interactions easier to build, particularly for educational, creative, and programming interfaces where conventional custom interaction code is costly.

Next-Concept Modeling: Fast, Parallel Coarse-to-Fine Text Generation

arxiv.org  ·  109 pts  ·  13 comments  ·  discussion

Analysis

The paper introduces Next-Concept Modeling (NCM), a non-autoregressive text-generation approach designed to address diffusion language models’ many expensive sampling passes. It first compresses text into a hierarchy of coarse-to-fine discrete residual VQ-VAE codes, then uses a transformer to predict all codes at each level in parallel before decoding the completed representation into tokens. In experiments with roughly 100M-parameter models, NCM reportedly matches or exceeds diffusion baselines while using 4–16× fewer function evaluations, running 10–31× faster on tasks such as LM1B, OpenWebText, XSum, and Sudoku, and requiring 4–5× fewer training tokens; MBR sampling can further improve quality. The main significance is a different quality–latency tradeoff for serving language models, though the results are early, benchmark-specific, and rely on a separately trained tokenizer and relatively small models.

Outlook.com is rejecting email from domains without DMARC

mailroute.net  ·  426 pts  ·  302 comments  ·  discussion

Analysis

Microsoft’s consumer email services—Outlook.com, Hotmail, Live, and MSN—are reportedly rejecting some messages from domains that lack a DMARC DNS record, including mail from small, low-volume senders. The intermittent bounces can occur even when SPF and DKIM are configured, because DMARC links those authentication mechanisms to the visible From address. Affected domain owners can typically start by publishing the TXT record `v=DMARC1; p=none`, while ensuring their sending service passes aligned SPF or DKIM. The change matters because missed invoices, applications, replies, or appointment notices may go unnoticed, and it reflects DMARC becoming a baseline requirement for reliable email delivery and protection against spoofing.
