The HN Take

Plugged in.

Here is a laptop power-management strategy:

The Nvidia RTX Spark laptop runs AI models quickly on Windows. It runs them about as quickly through Windows Subsystem for Linux. It also runs them quickly on native Linux, as long as you unplug it from the wall. If you plug it in, it slows down dramatically.

In one benchmark using GPT-OSS-120B, Windows generated 65.4 tokens per second, WSL generated 65.1 and Nvidia's DGX Spark desktop generated 61. Native Linux on the same laptop managed 13.9. A longer test took about eight minutes on Windows and 37 minutes on Linux.

This was not thermal throttling. The GPU stayed between 40 and 47 degrees Celsius. It was not running too hot; it was running too politely. On Windows, its clock held near 2.2 GHz. On plugged-in Linux, it sat around 790 MHz.

Oddly, disconnecting the laptop from external power mostly fixed it:

"Unplugged, Linux hit around 61 to 67 tokens per second on LM Studio, comparable to Windows. Plugged in, that same test dropped to about 15 tokens per second."

Sure. Normally a laptop has a battery-saving mode in which it sacrifices performance when unplugged. The RTX Spark apparently has a Linux-saving mode in which it sacrifices performance when plugged in. If your large language model is taking too long to answer, pull the power cord. The electricity was getting in the way.

The explanation is that Windows includes something called the Nvidia Platform Controllers and Framework, which manages the shared power budget between the CPU and GPU. Linux does not have an equivalent. The controller reads an encrypted table of power settings from the firmware; the Windows software can decrypt it, while Linux cannot. Disabling the controller in Windows reproduced the Linux behavior, dropping performance and locking the GPU near the same 786 MHz clock speed. Re-enabling it restored performance.

This is a pleasingly literal version of vendor lock-in. The computer contains plenty of power, and Linux contains a working open-source Nvidia driver, but the instructions for combining those things are encrypted. Windows has the key. Linux can use the GPU, just not with enthusiasm.

There is a similar issue with memory. The laptop has 128GB of unified memory and reserves 96GB for the GPU by default. Native Linux initially saw only 28GB, and the allocation setting was available only in Windows. The fix was to boot into Windows, lower the GPU reservation to 4GB, and then boot back into Linux, which could see 120GB. Thus Windows is required to configure the memory for Linux, and Windows is required to unlock full GPU performance for Linux. The most practical way to run Linux is consequently WSL, meaning Windows.

This is not ideal if you bought an unusually powerful AI laptop because much of the AI software ecosystem is Linux-first. But it does produce a coherent product architecture. Nvidia sells a Windows-on-ARM laptop whose special appeal is running Linux AI tools, and the best way to do that is to keep Windows running underneath them. Native Linux also works, provided you configure it from Windows and operate the laptop on battery. Portable computing, in the strict sense.

1. Nvidia RTX Spark encrypted firmware slows inference speed to 35% on Linux

mindstudio.ai | novaRom | 137 points | 68 comments | discussion

First seen: November 04, 2026 | Consecutive daily streak: 1 day

Analysis

The story examines Linux support on Nvidia RTX Spark laptops, finding that installation, display, peripherals, CUDA, and AI tools can work but require distribution-specific fixes and Windows configuration to expose the laptop’s unified memory. Native Linux suffers a major performance penalty when plugged in because a Windows-only Nvidia Platform Controllers and Framework component manages CPU/GPU power sharing using an encrypted firmware table that Linux cannot access, locking the GPU near 780 MHz instead of roughly 2.2 GHz. In testing, a large-model workload achieved about 13.9 tokens per second on native Linux versus 65.4 on Windows and 65.1 in WSL, while battery operation largely removed the disparity. The practical takeaway is that WSL currently offers Linux tooling with near-Windows performance, while a proper native-Linux solution requires Nvidia to provide equivalent power-management support.

3. Verification Is Not Knowledge: Science needs more than answers

blog.cosmos-institute.org | ersinesen | 66 points | 35 comments | discussion

First seen: November 04, 2026 | Consecutive daily streak: 1 day

Analysis

Jessica Hullman argues that verified AI-generated proofs, treatments, or research findings are not equivalent to scientific knowledge, because science also depends on understanding, accountability, interpretation, and criticism. The article critiques the “value-free” view that reliable procedures and correct outputs can replace human judgment, noting that researchers must be able to explain claims, respond when assumptions fail, and decide which results matter. Peer review and scientific progress are presented as social processes in which accountable people challenge, revise, and build on one another’s work. This matters as AI agents increasingly generate and validate research: without preserving human expertise and judgment, science could accumulate technically correct answers that communities cannot meaningfully evaluate, use, or connect to human goals.
