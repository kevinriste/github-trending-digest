The HN Take

No MCP.

Okay here's a software architecture strategy:

Pi used to advertise that it did not support the Model Context Protocol. Its developers dismissed MCP in podcasts and published a post explaining why they did not want it. Now Pi supports MCP in its core.

"What happened?" asks Pi's new post.

"Things Change."

Sure. MCP changed, but the more important development is that Pi's developers discovered that implementing MCP required them to build something they wanted anyway: a JavaScript sandbox for orchestrating tool calls. MCP servers expose tools, the model discovers them, and Codemode lets the model combine their structured outputs without dumping every tool and every result directly into the context. This is also useful for things other than MCP. Therefore Pi supports MCP.

This is a respectable technical explanation. Also it is the normal lifecycle of refusing to support a standard. First you say the standard is bad. Then everyone uses it. Then you implement it, but correctly.

Pi's remaining complaint is that MCP is "hard to compose." Many MCP servers were designed for harnesses that shovel tools into the prompt and return text, while Pi wants something "much closer to OpenAPI with intelligent tool discovery": structured data, searchable documentation and code that wires the calls together. The problem is no longer exactly MCP. The problem is that other people are using MCP wrong.

"We believe the best way to positively influence something is to embrace it," Pi writes. Right. Standing outside the standard and complaining did not improve the standard, so Pi has joined the standard in order to continue complaining from a position of greater authority.

This is how standards win. Not by convincing their critics that they were right, but by becoming unavoidable enough that the critics integrate them and explain that their integration is really a sophisticated critique.

Seven days.

GPT-6 Sol had a good run:

GPT-6.1 Sol has replaced it after seven days.

Artificial Analysis reports that the new model scores four points higher on its Intelligence Index, landing one point below GPT-6 Astra, while costing less than one quarter as much per Intelligence Index task at maximum effort. Pricing remains $2 per million input tokens and $10 per million output tokens, though cached input is now cheaper. It is smarter, slightly cheaper for agentic work and uses 10% to 30% more output tokens.

This is the mature software release cycle now. You launch the new frontier model, everyone rewrites their model routing around it, and one week later you replace it with a model carrying a decimal point.

The model also improved eight points in AA-Omniscience Accuracy while reducing its hallucination rate from 60% to 54%. This is progress. It hallucinates less often than before, though still often enough that, if a colleague behaved this way, you would stop asking them questions. But your colleague probably does not cost $0.72 per Intelligence Index task.

There is also an "xhigh" effort setting, which outperformed the "max" setting by three points on the Coding Agent Index. Apparently maximum effort is no longer the maximum effort. This makes sense in AI naming conventions, where "Sol" can be replaced in seven days, "Astra" can nearly be matched for less than one quarter of the cost, and the level above max is xhigh. Eventually the models will become intelligent enough to rename the settings, though perhaps that benchmark is not included.

1. Pi.dev: You Said No MCP

earendil.com | yarapavan | 72 points | 26 comments | discussion

First seen: September 30, 2026 | Consecutive daily streak: 1 day

Analysis

Pi.dev explains why Pi reversed its long-standing opposition to Model Context Protocol (MCP) and added it to the core. The change reflects improvements in MCP and the realization that supporting it required generally useful capabilities, especially better deferred tool loading and a JavaScript-based “Codemode” sandbox for composing tool calls. Pi’s approach emphasizes structured outputs, intelligent tool discovery, and orchestration within the trusted harness rather than simply exposing every tool in the model’s context. The shift is important because it lets Pi work more efficiently with modern LLMs and MCP ecosystems while giving the project a role in improving still-fragmented server and tool-use patterns.

Comment Analysis

Reactions were mixed: some valued MCP’s broad compatibility despite its imperfections, while others questioned what Codemode adds beyond shell scripts or CLI tools. The central technical disagreement concerned whether tool composition should happen through a harness-controlled environment or general-purpose shell access, with security raised in favor of constraints. Other comments debated sub-agent defaults, practical MCP gaps, and whether the post clearly explained the change.

Pragmatic support for MCP’s ecosystem — Some commenters saw broad compatibility and user access as worth accepting MCP’s current imperfections, which may improve over time. A newer user also described being surprised by the lack of MCP support.

3. Livenerf: Has Opus 5.5 been nerfed yet?

github.com | bryan0 | 654 points | 261 comments | discussion

First seen: September 30, 2026 | Consecutive daily streak: 1 day

Analysis

Livenerf is an open-source, preregistered benchmark designed to detect whether Claude Opus 5.5’s performance or reasoning effort declines after launch, addressing user reports of models being quietly “nerfed” through routing, serving, or configuration changes. It runs a fixed panel of difficult questions daily through a pinned Claude Code harness, compares results with a launch-week baseline and an Opus 5 control, and records accuracy, token usage, versions, and raw logs for statistical analysis. The project is calibrated and validated to detect meaningful degradation, though its early testing shows limited sensitivity to modest same-family model swaps and results are not yet available because the 30-day series is still collecting data. Its importance is methodological: it aims to replace anecdotal quality reports with reproducible evidence about how a commercial model behaves in its actual subscription serving environment.

Comment Analysis

The discussion split between commenters who attributed perceived post-launch declines to rising expectations, novelty wearing off, or untested anecdotes and those reporting regressions in their own use. Reported declines were variously attributed to load, routing, quantization, or ordinary bugs and product changes, without establishing a single cause. Commenters also debated whether benchmarks can reliably detect changes, and some suggested that serving may vary across users or plans.

4. Solving Factorio Quality

Analysis

The article develops a mathematical method for planning Factorio: Space Age’s Quality production systems, where quality modules introduce probabilistic upgrades and recyclers create potentially unbounded crafting loops. It models quality tiers, crafting, recycling, filtering, and asteroid reprocessing as vector and matrix transformations, then solves the resulting long-term equilibrium equations with Gaussian elimination rather than relying on iterative approximations. 8. Vermont replacing power plants with home batteries

Analysis

Vermont utility Green Mountain Power is aggregating batteries installed in more than 5,500 homes into a virtual power plant that provides backup during outages and supplies about 110 megawatts when the grid needs it. Customers lease paired batteries for $55 a month, gaining resilience and potentially lower energy costs, while the utility can reduce reliance on fossil-fuel peaker plants and avoid some infrastructure investment. Software coordinates home batteries, solar, electric vehicles, and demand-response resources, with customers retaining a reserve for emergencies. The model is important because it shows how distributed assets can improve reliability and reduce emissions and costs, though adoption is constrained by enrollment expenses, wholesale-market rules, and utility incentives that often favor building conventional infrastructure.
