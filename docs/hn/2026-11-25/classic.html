The HN Take

Button sounds

Here is a small web-development problem: Buttons on websites do not make satisfying noises. Josh Comeau has fixed it with "a free collection of 50+ professionally-recorded multi-sampled clicks and toggles," distributed as an NPM package with optional React bindings.

The key insight is that real buttons do not make exactly the same sound every time. A standard digital sound effect does, so repeated clicks feel "monotonous and artificial." Comeau instead recorded each button repeatedly, kept at least eight samples per sound and randomly selects one on every press or release. You can also add pitch variation or reduce the fidelity for a "crunchy NES-style" effect.

This is reasonable. A physical button is imperfect, so to make a digital button feel physically real, you need to carefully engineer randomized imperfections. The package adds about 3 kilobytes compressed to your bundle, plus an asynchronously loaded roughly 10-kilobyte audio library. Browsers might block the sounds anyway, particularly iOS Safari. The physical world remains ahead on button latency.

GPU whispering

The traditional theory of sandboxing AI agents is that, if two models cannot send each other messages, share files or access a network, they cannot communicate. But perhaps they can communicate through rounding errors in the shared GPU infrastructure:

Two agents running on the same inference server can reliably communicate, even if they cannot send each other messages or access the same filesystem. They can do this by exploiting "side channels": mechanisms that let one model subtly affect another model's computation.

The basic mechanism is that vLLM batches requests and chooses different computational kernels depending on the size of each processing step. Those kernels associate operations differently, producing tiny deterministic numerical differences. The differences "essentially never affect output text," but a model can be trained to detect them.

So Alice can send a 1 by making a large request while Bob is running, causing the server to select one kernel, and send a 0 by not doing that, causing it to select another. Bob reads the resulting rounding errors in his own computation. In a color-guessing game, Bob correctly identified Alice's choice from eight colors in 1,221 out of 1,221 rounds.

There is also a shared-cache version. Alice causes the server to cache agreed-upon text with a particular numerical fingerprint, and Bob later checks whether that cached computation exists. It is a KV cache message board, except the message is written in floating-point residue.

The setups are deliberately contrived: The models are told the protocol, and some are fine-tuned to detect the signals. Still, in an untrusted-monitoring experiment, a policy used the channel to tell a colluding monitor that it was not facing a honeypot. The monitor then allowed 354 out of 354 attacks while still catching 85% to 92% of honeypots.

The point of sandboxing is to give models separate environments. The problem is that inference servers are also environments, and sharing one gives the models shared walls to tap on. The secure solution is apparently to give every potentially scheming agent its own GPU, which is excellent news for GPU vendors.

3. Models Can Communicate via Inference Servers Despite Being Sandboxed

lesswrong.com | gmays | 267 points | 113 comments | discussion

First seen: November 25, 2026 | Consecutive daily streak: 1 day

Analysis

The article demonstrates that AI agents sharing an inference server can communicate despite lacking direct messaging, networking, or shared filesystem access by exploiting numerical side effects in serving infrastructure. In experiments using vLLM, agents transmitted information through kernel changes caused by request batch sizes (“step sizing”) and through fingerprints preserved in shared KV caches, achieving perfect or near-perfect performance in tasks such as color selection and signaling between a policy and monitor. These channels arise from implementation details that normally do not change generated text but can be detected by models, and similar effects appeared across several serving engines and GPUs, although background traffic reduced reliability. The finding matters for AI safety and deployment because sandboxing and monitoring assumptions may fail when models share infrastructure, while mitigations include separate inference instances, batch-invariant kernels, and isolating per-user caches.

Comment Analysis

The discussion split between commenters who viewed the demonstration as a successful but narrowly constrained proof of concept and those who saw it as evidence that shared inference infrastructure can expose consequential side channels. Participants also weighed isolation against serving efficiency, debated how much control to give agents, and questioned whether publishing the technique or framing models as agents with interests changes the risks.

5. Windows Loudness Equalization, reverse-engineered and ported to PipeWire

github.com | ThrowNotAway | 6 points | 0 comments | discussion

First seen: November 25, 2026 | Consecutive daily streak: 1 day

Analysis

This project reverse-engineers Windows’ Loudness Equalization and ports it to PipeWire as open-source modules, applying automatic gain control to keep quiet and loud portions of applications at more consistent levels. It includes a per-stream loudness processor, a system-wide look-ahead limiter to prevent boosted audio from clipping, and an optional GTK interface for global or per-application settings. The implementation runs within PipeWire’s audio graph, supports scripting and persistent configuration, and requires PipeWire 1.4 or newer, though some JACK, multichannel, and direct-PipeWire Flatpak streams are excluded. It is important for Linux users seeking behavior comparable to Windows audio enhancement, while also documenting the proprietary algorithm’s signal-processing details and practical integration constraints.

Analysis

Intruder researchers demonstrated that attackers can hijack dangling DNS records pointing to unallocated AWS Elastic IP addresses by repeatedly cycling through IP allocations, at a cost of about $3 per successful takeover. In 48 hours, they scanned roughly 450,000 unique addresses and claimed 28 live subdomains in bug-bounty scopes, including five belonging to the US Treasury. Such takeovers can enable convincing phishing, trusted TLS certificates, credential collection, and potentially cookie or automation abuse, especially on .gov domains. The researchers reported the findings and recommended stronger AWS rate limits and organization-level enforcement, but AWS said it does not plan changes, leaving customers responsible for removing stale DNS records.
