The HN Take

Looping

Here is one way to make an artificial intelligence model bigger without making it bigger:

GLM-5.4 is our first flagship model built on the Loop Transformer architecture, reaching intelligence levels comparable to 2T-3T parameter models.

GLM-5.4 is a 750 billion parameter model. Instead of giving it trillions of parameters, Z.ai takes 28 of its layers and runs them twice. "This gives us a deeper network without increasing the parameter count."

Sure. Normally a Transformer passes a thought through each layer once and moves on. GLM-5.4 sends the thought back through a shared block of layers for another look. The model does not have more brain, exactly; it just asks the same part of the brain to reconsider. This is computational rumination.

There are some practical problems. Repeatedly overwriting the hidden state can make activation norms "blow up across iterations," so GLM-5.4 uses gates to control how much each pass writes back. The first pass gathers context and writes cautiously; the second pass opens the gates and makes fuller updates. On harder tokens, the first pass writes more aggressively. Even the model knows that some emails can be skimmed while others require a strongly worded draft followed by a calmer revision.

Z.ai says the looping approach worked in a controlled test on a 30 billion parameter model. With the same number of parameters and about 10% more training compute, the looped model improved most on math, scientific reasoning and long-context tasks. It also used 10% to 14% fewer output tokens on several benchmarks, because "part of the reasoning shifts from explicit output tokens into the implicit depth of the loop."

That is appealing economics. The model thinks more while saying less. Previously the chain of thought sprawled across the page; now it conducts part of the meeting internally.

There is, however, a limitation:

Most notably, it tends to get caught in overly long "marathon thinking" loops, though this prolonged reflection and self-correction does consistently improve accuracy beyond its parameter count.

Right. You save parameters by making the existing parameters think again, and then sometimes they cannot stop thinking. This is better than being confidently wrong, perhaps, but less useful if you asked it to rename a variable and it retreats for a three-day silent meditation.

The broader ambition is "Generalized Coding," in which coding becomes the basis for video generation, games, 3D modeling, mechanical design and physical control. The model can use code as an intermediate language for doing other things. If everything can be represented as a program, then a coding model can do everything. If it cannot do something, it can loop over the problem until either it can or everyone goes home.

Mac inside Linux inside Mac

Here is a normal computer setup:

XNU Linux builds Apple's open-source XNU kernel and loads it as a Linux kernel module. The hosted XNU kernel then runs macOS processes natively alongside Linux processes on the same CPUs, while Linux supplies memory, timers, files, networking and GPU access.

With a stock Ubuntu kernel, "insmod xnu.ko" boots a macOS 27 system disk to a desktop with loginwindow, WindowServer, Dock, Finder, Safari and Chrome.

Fine. The requirements include an arm64 Linux host running on Apple Silicon "in a VM," plus a Mac with Xcode to prepare the system disk and GPU components. So the practical arrangement is approximately: Start with a Mac, run Linux in a virtual machine, load the macOS kernel into Linux, boot macOS, and then, from that macOS, SSH into the Linux that contains it.

The project's screenshot caption describes exactly this:

One system, two userspaces. Left: a Terminal in the hosted macOS 27.2.1. Right: from that macOS, an SSH session into the Linux it runs inside.

There is "no hypervisor between" the hosted macOS processes and Linux processes. There is, in the demonstrated setup, a hypervisor outside both of them, because Linux is running in a VM on the Mac. This is not contradictory. It is just computing's version of putting a small box inside a larger box and emphasizing that the two objects inside the small box are not separated by another box.

The system boots macOS to the desktop in 31 to 48 seconds, compared with 49 seconds for an Apple Virtualization macOS VM on the same Mac. Apps work, a 30-minute stress test finishes without a panic, and Metal reaches the host GPU through a sequence involving metal2vulkan, Vulkan, a DRM bridge, a Linux daemon and Mesa's Venus driver. If that is unavailable, it renders on the CPU. Finder does not need to know how many conceptual borders its pixels crossed.

There are compromises. The macOS system disk must come from the user's own installation; no Apple binaries are distributed. The OS cryptex is merged into the system volume, AMFI is patched, SIP is relaxed, and memory access is slower than in a native VM because Linux uses 4K pages while macOS normally uses 16K pages.

But the central result stands: You can boot Linux on a Mac so that Linux can boot macOS, and then use macOS to log back into Linux. At last, the operating systems have achieved vertical integration.

2. XNU Linux: Full OS X GUI Userspace on Linux

github.com | mmastrac | 380 points | 172 comments | discussion

First seen: November 23, 2026 | Consecutive daily streak: 1 day

Analysis

XNU Linux is an experimental project that runs Apple’s open-source XNU kernel and a full macOS GUI userspace as a loadable module inside an unmodified arm64 Linux kernel, allowing macOS and Linux processes to run natively on the same hardware without a hypervisor. Linux supplies resources and device access through a Foreign Kernel Interface, while hosted macOS can boot to the desktop and run applications such as Safari, with optional GPU support bridged through Vulkan. It currently targets Apple Silicon Linux environments, requires users to provide their own macOS installation, and remains a research-grade system with relaxed security protections, performance tradeoffs, and other production limitations. Its importance lies in demonstrating an unusual form of kernel co-hosting that could broaden virtualization and compatibility research, while also raising practical licensing, Apple platform, and maintenance constraints.

Analysis

The article examines whether the reported 17 million lines of Lean used in a recent formal proof of the Riemann hypothesis is unusually large. Comparing it with 259 human-written Mathlib formalizations of famous theorems and 938 Lean packages indexed by Reservoir, the author finds that typical mathematical proofs are far smaller. Some AI-assisted or generated projects exceed 17 million lines, but their size can reflect unfinished work, database-generated verification code, or highly verbose automated development rather than core mathematics. The comparison matters because line counts are a useful but imperfect measure of formalization effort, distinguishing human-readable proofs from machine-generated infrastructure and redundant code.

6. Elixir HLS makes FPGA circuits from functions written in Elixir

github.com | kristianpaul | 24 points | 0 comments | discussion

First seen: November 23, 2026 | Consecutive daily streak: 1 day

Analysis

Elixir HLS is an early-stage open-source tool that compiles constrained Elixir functions into SystemVerilog and FPGA circuits through high-level synthesis, while retaining ordinary CPU execution for testing and fallback. Developers use `defhls` to define integer-based computations and `definstance` to place them in hardware, with support for state, memories, fixed loops, streams, events, and device interfaces. The project currently targets boards such as the Sipeed Tang Primer 25K and has demonstrated an FPGA-based FM-radio demodulator, though it lacks features including floating point, division, recursion, and general collection processing. Its significance is the potential to let Elixir developers describe, simulate, and deploy hardware accelerators using a single functional-language specification, with automated comparison between software and generated circuits.

7. Masullo on the Riemann Hypothesis

johncarlosbaez.wordpress.com | xiaoyu2006 | 245 points | 221 comments | discussion

First seen: November 23, 2026 | Consecutive daily streak: 1 day

Analysis

The article explains Alessandro Masullo’s 940-page draft attempt to prove the generalized Riemann Hypothesis for zeta and Hecke \(L\)-functions using a new trace formula linking zeros to primes, building on ideas from Weil and Connes. The proposed strategy constructs an operator whose spectral side encodes \(L\)-function zeros and whose geometric side, decomposed prime by prime, is claimed to remain holomorphic in a region that would exclude zeros off the critical line. Its most delicate steps involve extending the trace formula to nonsmooth limiting test functions and controlling the resulting expressions uniformly. Early reviewers have reported possible errors, including a problem at the prime 2 and questionable functional-analysis claims, while the manuscript remains an unfinished draft. Even if it fails, the work is important as a detailed test of a major operator-and-trace-formula approach to one of mathematics’ central unsolved problems.
