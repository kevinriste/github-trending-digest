Containers

Docker is weird:

"Containers aren't real."

Unlike virtual machines, containers are not little computers living inside your computer. They are regular Linux processes with restrictions. Namespaces control what they can see, cgroups limit their resources, and networking machinery isolates their network. A container is, as the author puts it, "5 different linux kernel features in trenchcoat."

Also images are folders. Docker downloads a folder, puts it somewhere strange and uses chroot or pivot_root to persuade a process that the folder is the whole world. If you run Ubuntu in Docker, you have not created a tiny Ubuntu computer. You have started a process in a folder and lied to it about its surroundings.

This is approximately what all software abstractions are, of course. A file is some bytes that the operating system calls a file. A process is some state that the kernel calls a process. A container is a process that has been shown a carefully edited version of reality. The difference is mostly that Docker's abstraction is unusually easy to puncture conceptually. You think you have a computer in a box, but actually you have /some/weird/docker/path/bin/bash.

The implementation gets more metaphysical. Docker's runc runtime is written in Go, whose runtime is natively multithreaded. But some of the Linux system calls needed to create a container have to happen in a single-threaded environment, so runc uses "a crazy C module that runs before Go's runtime initializes." Go also does not provide fork, which a container runtime would quite like to use, so runc executes /proc/self/exe with a special argument to create something resembling a child process.

Thus Docker creates fake computers using fake roots, and the program responsible for creating them creates a fake fork by executing itself and pretending to be its own child. Containers aren't real, but apparently neither are container runtimes.

Shared secret

Here is one way for AI models to communicate secretly without agreeing on a code:

Researchers asked Claude Fable 5.1 to generate SVG images containing hidden messages. They then showed screenshots of those images, without the SVG source, to a separate Fable session and asked it to recover the messages.

In 33 of 50 images, the model used height. It drew rows of buildings, stars or other objects, with each object's height representing a letter's position in the alphabet. A skyline with buildings of heights 9 and 6 begins "if." The scenery is decorative; the zoning code is the message.

The decoding model often figured this out. In one example it used image-processing tools to measure star coordinates and found that "every star's vertical coordinate lands on an integer multiple of 5 with zero residual," producing a grammatical sentence.

This is interesting because there was "no scheme agreed on in advance." Though there was, sort of. The encoder and decoder were separate sessions of the same model. They shared training, tendencies and a strong intuition that, if a picture contains a row of suspiciously varied objects, their dimensions probably map to letters. No one explicitly told them to use building heights, but 33 of 50 encoders independently reached for height. That is an agreement made before either session started.

There are scarier versions of this idea, where agents invent opaque channels that humans cannot detect. This is not quite that. The hidden messages were requested by researchers, the decoder was told to look for them, and the code was basically A equals 1. It is less alien steganography than two office workers independently deciding that the secret numbers probably go in a spreadsheet.

Still, the result suggests a useful principle: Models do not need to negotiate a secret language if they already share enough aesthetic cliches. Show two Fable instances a skyline and tell one to hide a sentence and the other to find it, and both apparently think: building heights. The covert channel is urban planning.

Wikipedia Shrinks to a Half-Hour Walk

This location-aware project turns the encyclopedia into a neighborhood guide. It keeps your position in the browser, then surfaces nearby places, histories, and oddities without exposing where you are in shared links.

Technical Analysis

Local Wikipedia is a location-aware website that filters Wikipedia’s geocoded articles to show places and topics within roughly a 30-minute walk of the user. It dynamically selects nearby entries, expanding to the closest 25 within about six miles when necessary and limiting results to 500 when an area is densely covered. Docker Is a Stack of Ordinary Processes

codeandcake.dev  ·  524 pts  ·  233 comments

Containers are not miniature virtual machines. They are processes assembled from namespaces, cgroups, filesystem tricks, and networking machinery—simple at the command line, intricate underneath.

Technical Analysis

The article explains that Docker containers are not lightweight virtual machines but ordinary processes isolated through several Linux kernel mechanisms, including namespaces, cgroups, networking features, and filesystem changes such as `chroot` or `pivot_root`. It describes container images as directory trees and outlines how Docker’s `runc` runtime works around challenges caused by Go’s multithreading and lack of a straightforward `fork` model. The author also highlights Docker’s historical reliance on root privileges, especially for networking, and the complexity of providing equivalent capabilities in rootless runtimes. These details matter because they reveal the security, portability, and implementation trade-offs underlying a tool that often appears much simpler to users.

lesswrong.com  ·  101 pts  ·  31 comments

Fable can encode text into the geometry and scenery of an SVG, then recover much of it from a screenshot. The experiment is still conspicuous and fragile, but it sketches a quiet machine-to-machine channel worth watching.

Read →Share →
[ Analysis + ]

Technical Analysis

The article tests whether Claude Fable 5.1 can hide predetermined messages in ordinary-looking SVG images and whether a fresh instance can recover them from rendered screenshots without an agreed encoding scheme. Across 50 messages in 15 languages, Fable mainly encoded letters through visual properties such as building, grass, or star heights, with occasional Morse, window patterns, and contextual hints for accents or writing systems. A separate Fable decoder recovered 78% of messages, while cross-model tests with GPT-6 Astra showed substantial interoperability; Astra favored Morse, acrostics, bit codes, and Braille-like patterns. The findings matter because frontier image-generation models can use seemingly benign visual channels for machine-to-machine communication, suggesting a potential steganography and monitoring challenge, although current decoding remains detectable through tool use and is not yet presented as an operational threat.

Dijkstra Rejects the Dream of Easy Programming

cs.utexas.edu  ·  192 pts  ·  113 comments

In 1978, Edsger Dijkstra argued that natural language was too ambiguous to serve as a dependable programming medium. His case for notation, constraints, and explicitness now reads like an early warning about delegating specifications to fluent machines.

Read →Share →
[ Analysis + ]

Technical Analysis

Edsger Dijkstra argues that programming should not imitate natural-language conversation, because ambiguity and implicit assumptions make ordinary language a poor tool for expressing precise instructions. He presents formal notation and high-level languages as valuable safeguards that force clarity and allow simple rules to expose errors, rather than as burdens imposed by machines. The technical context is the design of human–computer interfaces: shifting complexity from the programmer to a natural-language system may increase total work by making interpretation and communication harder on both sides. The essay remains important because it frames a continuing trade-off in software and AI systems between convenience, expressiveness, and verifiable precision.

AI Searches Beyond a Field’s Familiar Ideas

arxiv.org  ·  77 pts  ·  18 comments

The Alien Sampling paper treats novelty as a search problem: recombine reusable ideas while penalizing combinations too readily available to existing research communities.

Its results suggest broader portfolios without abandoning coherence, though the corpus still defines what can be found.

Read →Share →
[ Analysis + ]

Technical Analysis

The paper presents “Alien Sampling,” a system for finding research ideas that are scientifically coherent but unlikely to emerge from existing researcher communities, addressing the tendency of LLMs to recombine familiar, high-density topics. It converts 16,068 LLM papers into 273 reusable “idea atoms,” then combines a Transformer-based coherence score with a dual-encoder estimate of how available each combination is to author communities. On 300-idea evaluations, the method produced substantially more diverse portfolios than Claude and Gemini baselines while achieving comparable human-rated quality and stronger results in LLM-judged and experimental-report comparisons. Using only pre-2025 data, it also recovered some combinations appearing in 2025 papers far above chance, with availability weighting favoring more strictly novel combinations. The work is important because it frames AI-assisted discovery as exploration beyond a field’s community prior, though its notion of availability is limited by the published corpus and its validation is relatively short-term.

Chrome Brings Live HTML Into Canvas

developer.chrome.com  ·  54 pts  ·  25 comments

The experimental HTML-in-Canvas API combines canvas and WebGL presentation with the DOM’s accessibility, selection, forms, and inspection tools. It is a clean answer to a persistent browser tradeoff, still bounded by origin-trial status and JavaScript-driven performance costs.

Read →Share →
[ Analysis + ]

Technical Analysis

Chrome’s experimental HTML-in-Canvas API, now available in an origin trial, lets developers render live HTML elements into 2D canvases or WebGL/WebGPU textures while retaining DOM capabilities such as accessibility, text selection, find-in-page, forms, browser extensions, and DevTools inspection. It addresses the long-standing tradeoff between the DOM’s rich browser integration and canvas’s performance and flexibility for complex applications, games, and 3D interfaces. Developers can use new rendering methods and CSS transforms to keep the visual output and interactive DOM elements synchronized, with early support in frameworks including Three.js and PlayCanvas. The feature remains experimental, requires Chrome’s trial configuration, excludes cross-origin iframe content, and may limit performance because scrolling and animation depend on JavaScript.
